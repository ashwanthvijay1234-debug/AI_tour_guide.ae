Part 01

The big picture

Before any single function makes sense, it helps to know what the program is shaped like.

There are only two pages

index.html is the landing page that explains the project. studio.html is the app. They share the first two stylesheets and nothing else. There is no server, no framework and no build step — the browser opens the file and runs it.

Load order is deliberate

FileOrderWhy it is in that position
tokens.css1stDefines the variables. Nothing can use a variable before it exists.
base.css2ndThe reset and shared controls, built on those variables.
studio.css3rdLast, so when two rules have equal weight this one wins and the page can override the shared defaults.
studio.jsdeferreddefer means "download now, run after the HTML is parsed", so the script never looks for an element that has not been created yet.

Everything is inside one wrapper

(function () { ... }())An IIFE — Immediately Invoked Function Expression. The function is created and called at once. Everything declared inside it is invisible to the rest of the page, so none of my variable names can clash with anything else.
'use strict';Turns on strict mode, which makes JavaScript report mistakes instead of quietly guessing — for example, using a variable I forgot to declare becomes an error rather than a silent global.

The path a plan takes

Settings4 inputs from the form
→
Promptsettings become instructions
→
Geminiwrites JSON

ParseJSON becomes data
→
Outputscreen · PDF · map

With no API key the middle box is replaced by the offline planner, which builds the same shape of data from a hard-coded list of real UAE places. Everything after that point is identical — which is exactly why the two modes look the same on screen, and why the app has to state which one produced the plan.

In one sentence Four settings become a prompt, a model turns the prompt into JSON, and the JSON is drawn on screen, typeset into a PDF and plotted on a map.

Part 02

Pressing Generate

One function, generate(), drives the entire application. This is its skeleton.

1 if (state.busy) return;A re-entry guard. If a plan is already being built, a second click does nothing. Without this, two runs would overlap and fight over the same output panel.
2 readConfig()Reads the four settings out of the form — destination, days, budget, and which interest chips are ticked — into one plain object.
3 apiKey()Reads the key box. This single value decides the entire path below: no key means offline, a key means Gemini.
4 pushMessage('me', …)Shows the user's own message in the chat immediately, before any waiting starts, so the interface responds to the click straight away.
5 showThinking()Adds the three bouncing dots. It carries aria-label="Assistant is typing" because three animated dots mean nothing to a screen reader.
6 setBusyPanels(true)Raises the blurred "generating" veil over both the Itinerary and PDF panels — you can switch tabs mid-run, and the PDF tab must never show the previous trip as if it were the new one.
7 if (!key) { … }The offline path. The 700 ms pause is deliberate: the planner finishes in about two milliseconds, and an answer that instant feels fake.
8 try { … }The AI path: work out which models the key can call, call them, parse the reply, show the plan.
9 catch (err) { … }If every model failed, show the offline plan anyway and say what went wrong. Being told honestly and given something that works beats being left with nothing.
Why async and await? Talking to Gemini takes seconds, and JavaScript cannot simply stop and wait — that would freeze the page. await lets me write the code top-to-bottom as if it were waiting, while the browser stays responsive underneath. Any function containing await must be marked async.
In one sentence generate() locks the interface, reads the settings, takes either the offline path or the Gemini path, and always finishes by showing a plan and unlocking again.

Part 03

Writing the prompt

This is the actual AI work of the project. The model is only as good as the instructions it is given.

'You are an expert …'The role. Telling a model who it is changes the whole answer. "An expert UAE travel planner" produces different writing from a general assistant.
lines.push(…)The prompt is built as an array of lines and joined at the end. This is far easier to read and change than one enormous string with + signs everywhere.
TRAVELLER NOTES,
most recent last		Everything typed in the chat is collected and sent every time. Saying most recent last and obey these above all tells the model which instruction wins when two notes conflict.
'Group each day
geographically'		A constraint, and the reason the plans are usable. Without it the model happily sends you across the city and back before lunch.
'Respect UAE realities'Local knowledge the model has but will not apply unless asked: heat, prayer times, dress codes, real drive times between emirates.
'Reply with ONLY
valid JSON'		The output contract. Giving the exact shape means the reply can be fed straight into the renderer instead of being read by a human.
lines.join('\\n')Joins everything with newlines into the single string that gets sent.
The idea to remember. An unconstrained model writes pleasant paragraphs. Pinned to a role, a currency, a pacing rule and an exact JSON shape, the same model becomes a reliable component that the rest of the program can depend on. That shift is what prompt engineering actually means.

One extra trick

Why The same prompt at the same settings gets much the same answer, so Regenerate looked broken. From the second attempt onwards the prompt explicitly asks for something different.

Part 04

Calling the API

The single most important piece of code in the project: the HTTP request that reaches Google.

fetch(url, options)The browser's built-in way of making an HTTP request. It returns a promise, which is why it needs await.
':generateContent'The Gemini endpoint that generates text. The model name goes in the path, so a different model is a different URL.
encodeURIComponent(…)Escapes anything in the model name or key that would otherwise break the URL. Never paste raw values into a URL.
'?key=' + keyHow Gemini authenticates. Because there is no backend, the key travels from this browser straight to Google and nowhere else.
method: 'POST'The prompt is data being sent, not a page being fetched, so it is a POST with a body.
JSON.stringify(body)Turns my JavaScript object into the JSON text the API expects. Its opposite, res.json(), turns the reply back into an object.
if (!res.ok) throwfetch does not throw on 404 or 500 — it resolves normally with ok: false. Forgetting this check is the classic fetch bug.
data.candidates[0]
.content.parts		Where the answer actually lives. Gemini can return several candidates, each holding parts; this takes the first candidate and joins its parts into one string.

What is sent, and what comes back

temperature: 0.9How adventurous the model is allowed to be. Near 0 it gives almost the same answer every time; 0.9 is high enough that two runs differ without becoming strange.
responseMimeTypeAsks the API itself to enforce JSON, as a second line of defence behind the instruction in the prompt.

Part 05

When things go wrong

Most of the interesting code in this project is not the happy path — it is everything around it.

chainA list of model names to try in order, already filtered so it only contains models this key can really call.
RETRYABLEOnly some failures are worth retrying: 404 (model gone), 429 (rate limited), 500/503/504 (Google having a bad moment). A 400 means my request was wrong, so trying another model would fail identically.
if (!firstError)
firstError = err;		Keeps the first error, never the last. The first came from the model the user actually chose. Reporting the last one made a bad key show up as "gemini-1.5-pro not found" — the name of a model nobody picked.
onHop(…)Posts a line into the chat: "gemini-X is busy — falling back to gemini-Y". A slow request should never look like a frozen one.
await sleep(400)A short pause before retrying, so a rate limit is not hit again immediately.
The bug this was written for. The first version had model names hard-coded. Google retired them, every request came back 404, and the app silently fell back to the offline planner forever — with a perfectly valid key sitting in the box. Now it asks the API which models exist before trusting any name.
.replace(/^\s*```…/)Strips a markdown code fence. Models add them out of habit even when told not to, and JSON.parse chokes on the backticks.
try { JSON.parse } catchFirst attempt on the cleaned text. If it throws, we do not give up — we fall through to attempt two.
indexOf('{') …
lastIndexOf('}')		Second attempt: take everything between the first opening brace and the last closing one. This rescues replies that begin "Sure! Here is your plan: {…".
return null;Signals "this was not JSON". The caller then displays the model's prose as text rather than showing an error, so a usable answer is never thrown away over its formatting.

Part 06

The offline planner

The part that works with no internet and no key — and the maths that stops it repeating itself.

The problem it had to solve

The planner is a pure function: the same settings in, the same plan out. That is normally a good property, but it meant pressing Generate twice produced an identical plan, which reads as "the AI is broken" — and in demo mode there is no AI to blame.

seeded(seed)Returns a function that produces numbers between 0 and 1 — the same job as Math.random(), except the sequence is decided entirely by the seed I hand it.
seed ^ 0x9e3779b9
Math.imul(…)		A hashing step. Seeds 1, 2 and 3 are very close together, and without scrambling them first the resulting sequences start out nearly identical.
s * 1664525
+ 1013904223		A linear congruential generator — multiply, add, wrap around. Simple, fast, and perfectly good for shuffling a list.
>>> 0Forces the result back into a 32-bit unsigned integer so the numbers wrap instead of growing forever.
s / 4294967296Divides by 2³² to land in the 0–1 range that the shuffle expects.
shuffled(list, rnd)A Fisher–Yates shuffle: walk the list backwards, swapping each item with a random earlier one. Every ordering is equally likely.
a = list.slice()Copies the array first, so the original pool of places is never reordered.
Why seeded instead of Math.random()? One seed always gives one ordering. That keeps the planner reproducible and testable — if I want to see the same plan again, I use the same seed. A session counter feeds the seed and is saved to localStorage, so reloading the page does not rewind the planner to its first plan.

Reacting to the chat, honestly

/…|…|…/iA regular expression listing words that suggest a slower trip. The i makes it case-insensitive.
.test(joined)Returns true if any of those words appear anywhere in the chat notes.
Be honest about this This is keyword spotting, not comprehension — and the app says so in the chat. Only the Gemini path genuinely understands a note like "make day 4 lighter, we have a toddler".

Drawing it and printing it

Turning the data back into something on screen, and then onto paper.

document
.createElement(tag)		Creates a real element object — a div, a span — rather than writing HTML as a string.
node.textContent = …Sets the element's text. Anything that looks like a tag is displayed as characters, not interpreted as markup.
never innerHTMLThis is the security point. The content comes from a language model, so it is untrusted input. If a model returned <img onerror=…> as a stop title, innerHTML would run it — textContent just displays it.
The principle. Treat AI output exactly like something typed by a stranger: display it, never execute it. Every single node in the itinerary, the map list and the chat is built with this helper.
unit: 'pt',
format: 'a4'		Work in points on an A4 page — the units a printed document is actually measured in.
doc.rect(…, 'F')Draws the navy header band. 'F' means fill it rather than outline it.
doc.text(str, x, y)Writes real, selectable text at a position. This is why the output can be searched and copied — it is not a screenshot.
need(height)My own page-break helper: before drawing a block, check it fits; if not, start a new page. This stops a day heading landing alone at the foot of a page.
createObjectURL(blob)Turns the finished document into a temporary URL the iframe can display, so you see exactly what will download.
revokeObjectURL(…)Releases the previous URL first. Without this, every regeneration leaks a whole PDF into memory for as long as the tab is open.

Small things that matter

Three short pieces of code that are easy to miss but worth being able to explain.

Storage that cannot break the page

try { … } catch (err) { }localStorage throws in private browsing and under file:// in some browsers. Nothing stored here — a remembered key, some notes — is important enough to break the whole page over, so failure is simply ignored.

The typing animation

requestAnimationFrameRuns the next step just before the screen repaints, so the animation stays smooth — and it pauses automatically in a background tab, which setInterval would not.
Math.min(9,
Math.max(1, …))		Clamps the speed between 1 and 9 characters a frame, so a short reply still feels typed and a long one does not outstay its welcome.
token.cancelledA cancellation flag. Starting a second generation cancels the first, so two messages can never type themselves at once.
if (stick) … scrollTopOnly auto-scrolls if the user was already at the bottom. Yanking the view back while someone is reading an earlier message is the fastest way to make a chat feel hostile.

Dragging the notes window

pointerdownPointer events cover mouse, touch and pen with one set of handlers, instead of writing mouse and touch versions separately.
setPointerCaptureKeeps sending events to the title bar even when the cursor moves off it — and it will, because people drag quickly.
event.clientX
- rect.left		Remembers where inside the bar you grabbed it, so the window does not jump so its corner snaps to the cursor.
Math.min(Math.max(…))Clamps the window inside the viewport so it can never be dragged somewhere unreachable.
If you are asked what you are most proud of Not the features — the failure handling. The app keeps working with no internet, no key, a retired model, or a reply that is not valid JSON, and it tells you honestly which of those happened.
